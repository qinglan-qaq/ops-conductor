# 运筹 OpsConductor · 电商 ERP 多 Agent 运营系统 · 设计规格

**版本** v1.0 ｜ **日期** 2026-11-03 ｜ **文档性质** 设计规格（Spec）｜ **状态** 已确认，项目骨架已初始化

---

## Problem Statement

我在求职聚水潭（电商 SaaS ERP）的 AI Agent 工程师岗位。JD 明确要求：真实商用项目经验（非 Demo）、多 Agent 系统设计（Planner/Executor/Memory/Tool/SKILLs/MCP）、复杂 ERP 任务拆解与反思纠错、类 RPA 流程编排、与 SaaS ERP 核心模块集成。

我当前的仓库里只有学习笔记、教学演示和求职文档，没有任何能证明上述能力的可运行系统。面试时无法展示：任务如何拆解、工具如何治理、失败如何补偿、写操作如何审批、效果如何量化。

约束条件：

- 不能接入聚水潭真实系统，也没有公司内部 SOP、能力规划资料或真实商家数据；
- 需要自建可演示环境，面试官能一条命令启动或看完整录屏；
- 需要边投简历边构建，时间充足但不能长期没有可展示成果；
- 项目必须通过公开开源数据、合成数据和自建 ERP 模拟器完成，且许可合规。

## Solution

构建 **运筹 OpsConductor：电商 ERP 多 Agent 运营系统**，以自建的多租户 Mini ERP 为业务底座，实现从自然语言指令到 ERP 业务动作的完整闭环。

三个演示场景：

1. **订单异常处理（主场景）**：识别超时未发货、库存不足、地址异常订单，生成拆单/换仓/改址/取消方案，低风险自动执行，高风险人工审批，失败补偿，输出处理报告。
2. **售后退款闭环**：查询订单与物流，混合检索售后政策，判定退款资格与金额，人工审批后调用退款，回写工单并通知客户。
3. **多仓库存调拨**：按销量与库存水位识别缺货仓与积压仓，生成调拨建议，审批后执行，校验库存一致性。

架构采用四层 + 支撑层：接入层（Web 控制台/飞书 webhook）→ 编排层（Planner、路由、DAG 执行器、人工升级）→ 执行层（领域 Agent + MCP 工具网关）→ 汇总层（冲突消解、验证门禁、渠道渲染、报告）。支撑层提供 RAG 混合检索、会话与失败记忆、可观测、评估。

核心取舍：**LLM 负责规划与异常判断，确定性运行时负责执行与超时控制**；验证 Agent 独立于生成 Agent 并拥有阻塞否决权；写操作按风险分级审批；无 API 的旧模块用浏览器自动化兜底（方案 B 的 RPA 部分）。

## User Stories

1. 作为求职者，我希望用一条命令启动完整演示环境，以便面试官能在 5 分钟内跑起来。
2. 作为求职者，我希望有一段 3–5 分钟的标准演示脚本，以便面试时按固定路径展示三个场景。
3. 作为求职者，我希望项目随时保持“可演示”状态，以便边投简历边迭代而不必等待全部完成。
4. 作为面试官，我希望看到每个任务的完整 trace（计划、工具调用、耗时、token、审批、失败），以便判断系统是否真实可用。
5. 作为面试官，我希望看到 100 条评测任务的量化结果，以便判断系统不是手工调出来的个例。
6. 作为面试官，我希望看到失败注入演示，以便确认异常路径被执行过而不是只写了文档。
7. 作为运营人员，我希望用自然语言下达任务（如“处理今天华东仓超时订单”），以便不学习复杂界面。
8. 作为运营人员，我希望在执行前看到结构化计划和影响范围，以便决定是否继续。
9. 作为运营人员，我希望看到每一步的前置条件、后置条件和预计影响，以便理解系统将要做什么。
10. 作为运营人员，我希望对高风险动作进行确认或拒绝，以便保留最终决策权。
11. 作为运营人员，我希望重复点击或渠道重推不会产生重复退款/重复拆单，以便避免资金与库存损失。
12. 作为运营人员，我希望执行到一半失败时系统能自动补偿或回滚，以便数据保持一致。
13. 作为运营人员，我希望失败时收到明确原因和已完成步骤清单，以便人工接手。
14. 作为运营人员，我希望任务结束后得到处理报告（成功、失败、跳过、待审批），以便复盘。
15. 作为客服，我希望退款资格判断附带政策原文引用和生效时间，以便向客户解释。
16. 作为客服，我希望金额计算展示明细（商品、运费、优惠、已退），以便核对。
17. 作为客服，我希望系统在低置信度或连续两轮未解决时转人工，并带上完整上下文，以便无缝接手。
18. 作为客服主管，我希望看到一次解决率、转人工率、误转率，以便评估效果。
19. 作为仓管，我希望调拨建议考虑库存水位、销量、在途和仓库容量，以便建议可执行。
20. 作为仓管，我希望并发调拨时系统检测库存冲突并重试或拒绝，以便不超卖。
21. 作为财务审核人，我希望退款、赔付类写操作必须经过审批并留痕，以便满足内控要求。
22. 作为租户管理员，我希望不同租户的商品、订单、知识库、缓存和日志完全隔离，以便满足数据安全要求。
23. 作为安全负责人，我希望每个 Agent 只拥有职责所需的最小工具权限，以便降低越权风险。
24. 作为安全负责人，我希望知识库或用户输入中的提示注入不会触发越权工具调用，以便防止数据泄露。
25. 作为安全负责人，我希望所有写操作可审计（谁、何时、依据什么证据、改了什么），以便事后追责。
26. 作为开发者，我希望 ERP 能力以 MCP 工具形式暴露，以便被不同 Agent 和外部客户端复用。
27. 作为开发者，我希望常见业务流程以 SKILL 模板形式沉淀，以便新场景通过组合而非重写实现。
28. 作为开发者，我希望系统记住失败模式（错误签名 → 处理策略），以便同类错误不重复发生。
29. 作为开发者，我希望按任务难度路由不同模型，以便在成功率不降的前提下降低单任务成本。
30. 作为开发者，我希望任务能从检查点恢复执行，以便审批等待或进程重启后不丢失进度。
31. 作为开发者，我希望有覆盖工具契约、策略计算、编排流程和检索质量的测试，以便修改提示词或模型后快速回归。
32. 作为演示观众，我希望看到“只有网页、没有 API”的旧版打单模块被浏览器自动化操作，以便理解 RPA 兜底能力。
33. 作为演示观众，我希望看到实时数据（库存、价格、物流）来自 API 而不是向量库，以便理解 RAG 的边界。
34. 作为演示观众，我希望看到知识检索结果带来源、版本和生效时间，以便判断答案可信度。
35. 作为演示观众，我希望看到多 Agent 结果冲突时的裁决过程，以便理解汇总层不是简单拼接。
36. 作为求职者，我希望每个关键设计都有决策记录（为什么 DAG 不是纯 ReAct、为什么验证独立），以便面试时讲清取舍。
37. 作为求职者，我希望项目指标能直接改写成简历条目和面试问答，以便降低材料准备成本。

## Implementation Decisions

### 1. 范围与优先级

- 首版只做三个场景，按「订单异常 → 售后退款 → 多仓调拨」顺序实现。场景数量不再增加。
- 每个场景必须先完成只读链路，再完成写操作；写操作必须先有审批与幂等，才允许接入演示脚本。
- 方案 B 只取两个组件：浏览器自动化兜底、工作流 DSL 编排与补偿，不单独做 RPA 平台产品。

### 2. 领域模型

自建 Mini ERP，核心实体：

- 租户 `tenant`、店铺 `shop`、用户与角色 `user/role`；
- 商品 `product`、SKU、类目、条码；
- 仓库 `warehouse`、库位、库存 `inventory`（可用/锁定/在途）、库存流水；
- 订单 `order`、订单行、支付记录、发货单 `shipment`、物流轨迹；
- 退款单 `refund`、售后工单 `ticket`、赔付记录；
- 知识文档 `policy/sop`（带版本、生效时间、适用租户/类目）；
- 任务 `task_run`、步骤 `task_step`、审批 `approval`、审计 `audit_log`、幂等键 `idempotency_key`。

一致性要求：库存与订单状态使用乐观锁（版本号），写操作必须携带幂等键，关键状态变更写审计流水。

### 3. 分层与职责

- **接入层**：统一消息信封（租户、渠道、用户、会话、消息 ID、内容、附件、时间戳）；负责鉴权、去重、限流、会话映射、渠道渲染能力抽象。不承载业务逻辑。
- **编排层**：意图路由（规则 + 小模型三分类：可直接回答/需工具/必须人工）、快慢双路径、任务 DAG 生成、并发调度、超时预算、人工升级、检查点恢复。
- **执行层**：领域 Agent（知识检索、商品、订单物流、售后、政策合规、动作执行）+ 验证 Agent；所有外部动作经 MCP 工具网关。
- **汇总层**：结果合并、冲突消解、证据与时效标注、质量门禁、渠道格式化、报告生成。
- **支撑层**：RAG 平台、记忆、可观测、评估、配置与模型路由。

### 4. Agent 角色与边界

- **Planner**：只负责把指令拆成 DAG、声明依赖与终止条件；不直接调用写工具。
- **Executor**：按 DAG 调用工具，处理重试、超时、补偿；不修改计划语义。
- **Verifier**：独立提示词、独立上下文、独立模型；检查证据支撑、金额一致、权限、政策合规、承诺边界；不通过则阻塞。
- **Memory**：会话摘要、任务历史、失败记忆、可复用计划检索。
- **Skill 库**：把“异常订单处理”“退款判定”“调拨建议”沉淀为参数化流程模板。
- **Handoff**：低置信度、连续失败、情绪升级、高风险动作 → 转人工并附上下文与已查结果。

### 5. 任务规格与 DAG

每个任务包含：任务类型、输入实体、风险等级、允许工具集、超时预算、终止条件。

每个节点包含：节点 ID、执行者（Agent 或工具）、输入引用、依赖边、前置条件、后置条件、超时、重试策略、补偿动作、风险等级、是否需要审批。

执行语义：依赖满足才执行；可并行的节点并行；节点失败按失败分类处理；后置条件不满足视为失败；任务结束必须满足终止条件并产出报告。

### 6. 工具与 MCP 契约

- 所有 ERP 能力封装为 MCP Server 工具，Agent 作为客户端调用。
- 工具元数据必须包含：名称、描述、参数 Schema、返回 Schema、风险等级、是否写操作、是否需要审批、是否支持 dry-run、幂等语义、超时。
- 写工具必须支持 `idempotency_key` 与 `dry_run`；执行前可预演影响范围。
- 工具网关统一做鉴权、租户注入、限流、审计、参数校验与敏感字段脱敏。
- 工具清单首版约 20 个：商品检索、SKU 详情、库存查询、库存预占、订单列表/详情、发货单、物流轨迹、退款政策检索、退款资格判断、退款申请、退款执行、拆单、换仓、改址、工单创建、客户通知、调拨建议、调拨执行、审计查询等。

### 7. 风险分级与审批

- L0 只读：自动执行。
- L1 低风险写：自动执行 + 事后通知（如创建内部工单）。
- L2 中风险写：需用户二次确认（如改址、拆单）。
- L3 高风险写：需人工审批，支持超时升级（如退款、赔付、批量调拨）。
- 审批记录必须包含：动作、参数、影响范围、依据证据、审批人、时间、结果。
- 审批等待期间任务进入可恢复状态，进程重启后从检查点继续。

### 8. RAG 与混合检索

- **通道选择优先于检索**：库存、价格、订单、物流走实时 API/SQL；商品参数走结构化字段 + 向量兜底；政策、SOP、FAQ、历史工单走混合检索；促销规则走规则引擎。
- **流水线**：查询理解（意图、实体、指代消解、必要时改写）→ 检索前元数据过滤（租户、渠道、权限、类目、生效时间）→ BM25 + 向量双路召回 → RRF 融合 → cross-encoder 重排 → 证据组装（来源、版本、时间戳、权限标记）→ 验证。
- **索引新鲜度**：政策与商品变更走增量索引；文档带生效/失效时间；缓存带版本号，失效即清。
- **缓存分层**：精确缓存、语义缓存（保守阈值）、工具结果短 TTL 缓存。
- **安全**：召回内容与用户输入均视为不可信；工具调用走 allowlist；输出做敏感信息过滤。

### 9. 记忆与反思

- 工作记忆：当前会话摘要与任务上下文。
- 情节记忆：历史任务计划、工具序列、结果，可按相似度检索作为参考。
- 失败记忆：错误签名（工具、错误码、消息模式）→ 处理策略 → 成功次数，避免重复犯错。
- 反思循环：失败分类 → 重试/重规划/降级/升级人工；设置最大重试次数与总预算；禁止无进展的循环重规划。
- 失败分类：瞬时（超时、限流）、业务（库存不足、政策拒绝）、模型（计划非法、参数非法）、权限、数据冲突。

### 10. 浏览器自动化（方案 B 组件）

- 选一个只有 Web UI 的旧模块（如老版打单页），用 Playwright 实现确定性操作。
- 原则：API 优先，浏览器兜底；浏览器步骤必须有选择器、超时、截图证据和失败重试。
- 不引入视觉大模型做主路径；必要时用 Stagehand/browser-use 处理未脚本化页面，但必须有人工确认与速率限制。

### 11. 多租户、安全与合规

- 所有数据表、缓存键、检索过滤、工具调用、日志均带 `tenant_id`。
- 角色权限决定可见工具与数据范围；越权请求直接拒绝并审计。
- 写操作最小权限、审批、幂等、审计四件套缺一不可。
- 提示注入防护：输入分级、工具白名单、输出过滤、验证 Agent 检查。
- 演示数据全部使用开源或合成数据，不包含真实个人信息。

### 12. 可观测与评估

- 全链路 trace：任务、节点、模型调用、工具调用、审批、补偿；记录耗时、token、成本、错误。
- 指标：任务成功率、工具成功率、首响与端到端 P50/P95、人工介入率、审批通过率、补偿成功率、单任务成本、引用准确率。
- 评估集：100 条 Golden Tasks，覆盖三场景与异常路径；断言最终业务状态、必需工具调用、禁止动作、引用来源。
- 变更（模型、提示词、检索策略）必须跑回归；线上灰度与 A/B 作为后续能力。

### 13. 技术栈

- 后端：Python 3.11+、FastAPI、SQLAlchemy、PostgreSQL 16 + pgvector、Redis。
- 编排：LangGraph（状态图、检查点、interrupt 审批）。
- 工具：MCP Python SDK 自建 ERP MCP Server。
- 检索：BGE-M3（dense+sparse）、bge-reranker-v2-m3、jieba + BM25（或 OpenSearch）；RRF 融合。
- 浏览器：Playwright，必要时 Stagehand。
- 可观测：OpenTelemetry + Langfuse（自托管）。
- 评估：Ragas / DeepEval / promptfoo，优先支持工具轨迹断言。
- 部署：Docker Compose 一键启动；演示控制台首版用轻量 Web UI，不追求前端工程量。
- 模型：通过统一网关配置，规划用强模型、路由与抽取用小模型、验证用独立模型；全部可替换。

### 14. 数据来源与灌数

- 订单与订单行：Olist 公开数据集（非商业许可，需署名，原始数据不入库不入仓），UCI Online Retail II（CC BY 4.0）作为补充。
- 商品目录：Amazon Reviews 2023 元数据或 Open Food Facts 抽样，统一映射到自建类目体系；类目参考 Google Product Taxonomy。
- 中文客服与商品知识：InfiniFlow Ecommerce Customer-Service-Workflow（Apache-2.0）。
- 客户、地址、电话：Faker `zh_CN` 合成，禁止使用真实 PII。
- 政策与 SOP：参考淘宝/天猫、京东、拼多多、抖音电商、Shopify、Amazon 的公开规则页面，**改写为合成 SOP**，不复制原文、不 redistributing 原文。
- 聚水潭开放平台文档：仅用于对齐 API 形态与术语（签名、订单查询、商品映射等），不申请真实商家凭据、不调用生产接口。
- 所有数据通过脚本生成或下载，仓库只保留 schema、种子脚本和小样本。

### 15. 交付物

- 可一键启动的 Docker Compose 环境与种子数据。
- 三个场景的演示脚本与 3–5 分钟录屏。
- 100 条 Golden Tasks 与自动评测报告。
- Trace 面板截图与失败注入演示。
- README（业务背景、架构图、指标、快速开始）。
- 3–5 篇架构决策记录（DAG vs ReAct、验证隔离、写操作审批、RAG 通道选择）。
- 简历条目与面试问答卡。

## Testing Decisions

**首选测试接缝（最高层，唯一主接缝）**：编排器的公开任务接口——提交任务、恢复任务、查询任务状态。所有端到端测试从这里驱动，断言三类外部可观察结果：最终业务数据状态、审计与审批记录、返回给用户的响应。测试内部使用确定性的 stub 模型（固定计划与工具参数），避免测试依赖模型随机性。

**次级接缝**：

- MCP 工具契约测试：参数 Schema、返回 Schema、幂等、dry-run、权限拒绝、错误码。
- 策略与金额计算：纯函数单元测试，覆盖优惠、部分退款、运费、已退金额。
- 检索质量：固定查询集 + 期望文档，测召回率与重排后 Top-N 准确率。
- 浏览器自动化：针对旧模块的页面级测试，断言操作后业务状态变化。

**好测试的标准**：只断言外部行为与业务不变量，不断言内部实现细节；每个写操作测试必须同时断言审计记录与幂等行为；失败注入测试必须断言补偿后的最终一致性。

**现有基础**：仓库中无同类测试先例，首版建立 pytest + Docker Compose 测试夹具的基线。

## Out of Scope

- 接入聚水潭真实系统或抓取其生产数据。
- 真实支付、真实物流、真实发票。
- 完整 ERP（财务、采购、生产、跨境税务）。
- 飞书/企微生产级应用上架与审批流；首版只做 webhook 演示。
- 模型微调与自研 embedding。
- 跨租户学习与数据复用。
- 多机分布式部署与大规模压测（只做单机并发验证）。
- 桌面自动化（仅浏览器自动化）。

### B. 边投简历边构建的节奏（全职投入版，约 6 周）

原则：**每周产出一个可演示增量，简历不等待项目完工。** 按每天 6–8 小时投入估算；若只能业余投入，将每周计划拉长一倍。

- **第 0 周（2–3 天）**：确定项目名与一句话介绍；搭骨架（Docker Compose + 空服务）；写 README 与架构图初稿；简历加入“进行中”项目条目。
- **第 1 周**：Mini ERP 核心表（订单、库存、商品、租户）+ 种子数据 + MCP 只读工具 + 订单查询演示。产出 v0.1 录屏（30 秒）。
- **第 2 周**：Planner/Executor/Verifier + 订单异常场景（只读 + 方案生成 + 审批界面 + trace）。产出 v0.5 三分钟录屏，**开始带项目投递**。
- **第 3 周**：退款场景 + RAG 混合检索 + 引用与金额明细 + 独立验证。产出 v0.8，简历更新为“已上线演示”。
- **第 4 周**：写操作（退款、拆单、改址）+ 幂等 + 补偿 + 审计 + 多租户隔离。产出 v1.0。
- **第 5 周**：多仓调拨 + 并发冲突 + 浏览器自动化兜底 + 失败记忆与模型分级。
- **第 6 周**：100 条评测集 + Langfuse trace + 失败注入 + 成本对比；文档、ADR、技术文章、面试问答卡；开源发布。
- **缓冲**：若某周延期，优先砍场景深度而不是砍审批、幂等、补偿、评测这四项“非 Demo 证据”。

投递节奏：每天固定 1–2 小时投递与沟通（建议 5–10 份精准投递，而非海投），其余时间构建；每完成一个里程碑更新简历、项目链接与一页纸进展；优先投电商 SaaS、ERP、客服 SaaS、RPA 方向，岗位关键词：AI Agent 工程师、LLM 应用工程师、AI 后端、智能体平台。

### C. 指标目标（按实际结果填写，不编造）

任务成功率 ≥ 90%；工具调用成功率 ≥ 99%；端到端 P95 ≤ 8s；高风险操作审批覆盖率 100%；越权写入 0；人工介入率 < 15%；单任务成本较初版下降 ≥ 30%；引用准确率 ≥ 95%。

### D. 风险与对策

- **范围膨胀**：场景锁定三个，新增需求进入 backlog 不进入当前版本。
- **模型不稳定**：stub 模型跑测试，真实模型跑评测；提示词与模型变更必须回归。
- **数据许可**：原始数据不入仓，提供下载脚本；非商业数据集只用于本地演示并署名。
- **演示环境故障**：提供录屏与预置快照，面试现场可离线运行。
- **“像 Demo”质疑**：用失败注入、幂等、补偿、审计、评测报告五项证据回应。
